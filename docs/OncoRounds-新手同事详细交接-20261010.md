## 1. 先了解你接手的是什么
项目把病例资料整理为病例摘要和病程轴，再结合医学指南、临床研究生成五道进阶单选题，供 OncoRounds 模拟查房页面展示。你接手的是整套工作流、提示词、代码节点、输出协议及相关调试资料，不只是一个出题提示词。

整体链路：
专用 OCR → 同一病例的文字 → 外层清洗及结构化 → 五题子应用检索/生成/修订/程序检查 → 外层组装 Questions + detail → 前端展示。

当前外层接收 OCR 文字，不直接读取图片。不应把“图片上传”“文字清洗”“医学内容审核”当成同一个功能。
当前导出文件已经离线检查，但本次交接没有调用在线模型、没有发布 FastGPT 应用，也没有完成独立医学审核。

## 3. 新手必须理解的几个概念
| 名词 | 在本项目里的含义 |
|---|---|
| 应用 | 一套可运行的 FastGPT 工作流；这里分外层和出题子应用 |
| 节点 | 工作流里的一个步骤，可以调用模型、执行代码、检索或输出 |
| 输入/输出 | 节点接收和返回的变量，不一定是聊天框可见内容 |
| 变量引用 | 从上游节点选择一个实际输出；必须用变量选择器绑定，不能只写同名文字 |
| 全局变量 | 外层运行前填写的 draftData 等输入；不是下游代码自动生成的字段 |
| JSON 对象 | 程序可以按键读取的数据 |
| JSON 字符串 | 对象经序列化后的文字；需要 JSON.parse 才能按键读取 |
| 检索片段 | 数据库返回的原文片段；必须与引用身份匹配 |
| 程序检查 | 核对格式、题数、绑定、原句等；不等于医学结论正确 |
| Debug/运行记录 | 查看某节点真实输入输出的地方；排错优先使用已有记录 |

不要凭节点绿色成功图标判断业务成功。例如某调用可以 success=true，但 data=""，后续仍然没有题目。

## 4. 首次导入和配置：按这个顺序做
### 4.1 先建立测试副本
保留线上已用版本，先导出备份。在 FastGPT 中创建测试用子应用和测试用外层应用，再分别导入 JSON。不同部署的导入入口名称可能不同，以实际界面为准；JSON 是流程配置，不会把云端模型权限、知识库正文和凭据一起搬过去。

### 4.2 先配置子应用
导入“五题出题子应用-完整工作流.json”，检查：
- 模型节点是否能使用 qwen3.8-flash。最新导出采用此模型；历史对话提过 GLM 不代表当前文件仍用 GLM。
- “良医汇医学数据库”工具节点能否正常调用；有权限、工具参数和返回字段是否兼容。
- “知识库搜索”的 datasets 是否绑定到新账号可访问的知识库。
- 导入后是否出现失效引用、必填变量未配置或工具不可用。
- 结果输出节点是否引用“整理最终输出”的 publication_payload_json。

不要只导入图形就认为环境迁移完成。跨账号导入后尤其要逐项确认外部资源。

### 4.3 再配置外层
导入“01-外层完整工作流.json”：
1. 全局变量保留 draftData，类型 String，必填。最新导出内部键为 hIxsHt3a；不要手工改键后忘记上游引用。
2. 检查“题目生成”应用调用节点，选择刚配置好的五题子应用。
3. 该节点用户问题应传入上游“代码运行”的 case_payload_json，而不是原始 OCR 字符串数组，也不是空聊天内容。
4. 检查“正文清洗（OCR文本）”“病例结构化提取”的模型权限。
5. 检查所有代码节点自定义输入引用是否完整。最新 json生成 没有 transport_mode 输入；不要照旧截图新增空的必填行。
6. 输出节点“json输出”应引用 json生成 的 response_json。

### 4.4 填一次最小测试输入
在全局变量 draftData 中粘贴一个已脱敏病例的 OCR 文字，然后发送“开始”触发。也可以输入同一病例多页文字的 JSON 字符串数组：
~~~json
["第一页病例文字","第二页病例文字"]
~~~
两项必须属于同一个病例。数组不代表批量处理两名患者。最新外层不开放文件/图片选择，不要把图片路径当作 OCR 正文。
先用一例有明确来源且已有输出的病例检查连通性，不要第一次就跑十例。实际模型和检索测试可能计费；先检查输入与配置，再运行。

## 7. 输出协议：三层数据不要混用
### 子应用内部候选
首轮/修订候选使用 schema_version 1.1，含 evidence_id、support_mode、verification 等内部核对信息。options 可以组织临床表达；verification 引文必须真实来自绑定证据，不能为了过检查而自行重写。
少于五题的非空草稿可能标 generation_status=success，这是候选生成状态；下游仍会判定未完成。不能单看这个 success 发布。

### 子应用最终传输封套
publication_payload_json 是字符串，解析后 record_type=oncorounds_final。
重点看：
- output_ready：完整五题且程序门禁通过时才可供下一步处理。
- program_check：程序检查结果及错误列表。
- completion：目标五题与实际题数。
- diagnostics：引用核对、绑定记录、原始输出、检索健康等排错信息。
- medical_review_status=not_performed、publishable=false：目前没有独立医学审核，不要删标志伪造已审核。
- final_response_json / final_questions_json 仍是字符串，按协议解析，不能直接当对象取 questions。

### 外层页面数据
外层实际返回 response_json，解析后是：
~~~json
{"Questions":{},"detail":{}}
~~~
Questions 对应题组；detail 对应摘要、病程轴、图片等。此处与上面的 oncorounds_final 不是同一个结构。
源码中虽然还构造 transport/execution_report 变量，当前外层 return 只返回 response_json；别根据未返回变量设计前端读取。
当前外层图片栏被置空；病例展示背景图片属于前端页面资源，与 OCR 上传图片区分。

字段兼容和癌种分类以当前代码、癌种字段规范和实际 API 消费协议为准，不随意新增公开字段。
A/B/C/D 解析放在已有 explain 内，按四行逐项解释。JSON 源文件中的 \n 解析后应为真正换行；前端仍需使用保留换行的样式，如 white-space: pre-line，否则会连成一段。
正确答案文字与 options[answer] 一致。若复盘页要展示“A. 已生成的选项文字”，应由 answer 与 options[answer] 拼接，不让模型另写一版答案。

3. OCR 与清洗之间可能遗漏整段治疗史，或把建议当作已实施治疗。出现这种情况要对照 OCR 原文字段，不能只修展示页面。
4. 同事新环境中的模型、数据库工具、知识库与子应用绑定尚未验证。
5. 最新离线报告 api_calls=0，model_run_performed=false，不能宣称已在线端到端验证。
6. 本交接没有修改/发布线上应用，没有重做本地前端。
7. GitHub 备份是快照；当前原始工作目录与另建的上传副本不是自动双向同步。

## 9. 常见错误：先看哪个节点
| 现象 | 首先查看 | 处理原则 |
|---|---|---|
| draftData 未填 | 外层全局变量 | 填脱敏 OCR 正文，再触发 |
| 导入后必填输入未配置 | 标红节点自定义输入 | 用选择器绑定实际输出，删除误加的空行前确认其用途 |
| learning_points / case_timeline 类型错误 | 病例结构化提取 → JSON格式修复 → 代码运行 | 对照真实对象/数组，不用 JSON.stringify 冒充可读展示 |
| CASE_SOURCE_REWRITE | 清洗正文与原始 OCR | 比较被拦截段落；优先修清洗保真，别去掉来源校验 |
| INVALID_JSON | 出错节点真实输入与上游完整输出 | 区分空字符串、错误封套、截断、非法转义、多对象拼接 |
| OPTION_QUOTE_NOT_FOUND | 首轮格式预检/最终程序检查与引用装配 | 同时查看 candidate_json、evidence_pool、verification；不能只看最终零题结果 |
| ANCHOR_SOURCE | 证据注册与压缩-最终 | 绑定是否唯一、是否有正文、doc_id 与 split_index 是否匹配 |
| VERIFICATION_MISSING | 题目生成-首轮/题目修订-第二轮 | 检查真实候选的四选项与病例核对内容 |
| 403 额度不足 | 模型服务返回错误 | 核实额度/授权，先停重复调用，不改提示词试图修余额 |
| 日期时间未详但正文有日期 | 代码运行和 json生成 | 日期分隔符、“起”、相对时点是否被正确解析 |
| 标题是诊疗节点1/诊疗记录 | 结构化结果和 json生成 | 独立提取事件短标题，不把整行正文截成标题 |
| 病理出现内部键/花括号 | biomarkers → json生成 | 转成中文可读描述，保留标本和时点 |
| A/B/C/D 一段连排 | explain 原始值 + 前端样式 | 判断是数据没有换行，还是渲染折叠了换行 |
| 全部任务 success=true 但 data 空 | 应用调用与结束节点 | 保存完整调用输出与错误；空结果不能统一伪报 JSON 格式错 |

一次真实失败应保存：节点名、完整自定义输入、完整输出/错误、当前 JSON 版本。不要只发裁掉正文的截图。
已有运行记录能定位时先用它；先修最小责任节点，再按需要做单节点或一例端到端验证，不反复跑十例。

## 10. 判断问题来自 OCR 还是工作流
依次对照“原图 → OCR 原文 → cleaned_text → 结构化病例 → 最终 detail/Questions”：
- 原图有、OCR 没有：OCR 提取/分页问题。
- OCR 有、清洗没有：正文清洗遗漏或误分类。
- 清洗有、结构化没有：提取/类型归一问题。
- 结构化有、页面没有：json生成 或前端展示问题。
- 前面没有、题目却有：模型补造或把假设当事实。
模糊数字、日期、药名应标待核对。影像报告“疑似”不能变成“确诊”；不能因单例治疗后进展，就断言药物导致进展。

## 11. 日常维护：不写代码也能先完成的工作
每天开始先 git pull，并确认工作流版本。在测试应用里修改，一次只改一个可定位问题。修改前导出备份；记录节点名、字段、原因和预期结果。
提示词修改先核对首轮与第二轮是否需要同步；只修首轮可能被第二轮改回。
修改代码节点同时检查输入引用、类型和输出声明；画布上线可能不代表变量名正确。
通过单节点检查后，用一例验证，再由医学同事核对患者事实和证据支持。最后保存并导出新版本，写明变更和测试范围。

git commit -m "说明修改节点、目的和验证"
git push
~~~
路径有空格需加引号。先确认远端是私有工作仓库。不要提交 API 密钥和新增可识别患者身份资料。

## 12. 接手验收与建议顺序
第一天：拿到 GitHub/FastGPT/数据库权限，克隆并读本指南，识别两份最新 JSON，在测试副本导入并检查变量。
第二步：用一例脱敏病例核对 OCR 到结构化的完整链路，再检查子应用绑定和检索结果。
第三步：核对 candidate_json 与 verification，理解格式失败和证据不足的区别。
优先待办：复核 CIP Q3 事实/教学假设，做一次新环境端到端验证并记录真实输出。不要先全面放宽原句规则或增加更多修复提示词。

交接完成应能回答：
- 我用的是哪两份版本文件？
- 外层的 draftData 填在哪里，为什么不能填图片路径？
- 题目生成 节点如何绑定子应用？
- 一道题绑定哪条证据，原文是否真的支持结论？
- 五题程序完成与医学审核完成有何区别？
- 发生零题时，能否找到具体错误节点的完整输入输出？
- 修改怎么备份、导出、提交、回退？

上线验收需另行确认线上应用、数据库连接、前端解析与医学审核；本交接文档本身不是上线验收记录。
