# 大查房病例资料预处理（2026-09-24 测试版）

## 导入与使用

1. 新建独立测试工作流，导入同目录的 `大查房-病例资料预处理-图片PDFHTML-测试版.json`。不要覆盖生产三连或题目生成应用。
2. 系统配置中的文件上传已在导出中开启：文档、图片、PDF增强解析，最多8个文件。导入后核对配置是否保留。
3. 核对「图片OCR-高精版」是否可用（沿用参考文件的 `systemTool-lyhOcr/advanced`），两个模型节点是否能使用 `qwen3.5-plus-nothinking`。导出不包含服务密钥。
4. 上传同一病例的图片、PDF或HTML，发送“整理病例”。`draftData`可留空；如果从原有HTML接口调用，也可只给`draftData`传正文，不上传文件。不要把文件URL写入用户问题来代替上传。
5. 查看最终JSON。核对病例变量和待核实项，再将`case_variables`内的字段映射到出题流程。这是预处理工作流，不会自动调用三连或修改线上病例。

## 支持范围

| 输入 | 处理方式 |
|---|---|
| JPG/JPEG、PNG、WEBP、BMP、TIF/TIFF链接 | 路由到原参考工作流的OCR工具；具体图片格式、大小限制以你们OCR服务实际能力为准 |
| PDF | 文档解析，保留PDF增强解析开关；扫描PDF依赖平台已配置的增强解析服务 |
| HTML/HTM文件 | 文档解析，提取正文；解析结果保留的HTTP(S)图片引用继续OCR |
| draftData中的HTML/文本 | 直接清洗正文；HTML内的绝对HTTP(S)图片链接继续OCR |
| 混合输入 | 允许同一患者的文档和多张照片合并；依次执行文档处理、图片处理、结构化提取、独立核对 |

链接支持大小写扩展名、查询参数、片段及路径编码。无扩展名/无法识别类型的链接会标记问题，不猜成图片。只能处理本次输入，不读取历史病例。

HTML相对路径、base64图片、依赖登录访问的图片、通过JavaScript动态加载的图片不保证可读取。相对引用被发现时会提示单独上传；如果文档解析器本身丢掉了图片引用，后续无法自动发现遗漏。当前未做网页抓取或PDF逐页转图服务。

## 流程

流程开始 → 文件类型分流 → 有PDF/HTML则文档解析 → 正文整理及内嵌图片提取 → 有图片则OCR → 完整性检查 → 病例变量提取 → 独立核对 → 结构与脱敏检查 → JSON输出。

无文档或无图片的分支会旁路。解析/OCR显式错误、空页、OCR返回数量不符、未知文件类型或超限会返回不足原因，不继续调用提取模型。文档解析有文字不等于每页完整；尚无PDF逐页覆盖率验证。

图片含内嵌图总数最多24，正文上限65000字符；超限报错而非静默截断。这是本测试版的保护值，不是平台官方上限。

## 输出与映射

根对象包含：
- `extraction_status`：`draft_requires_confirmation`（提取核对未发现问题）、`needs_review`（需修订核实）、`insufficient`（资料/解析不足）。
- `case_variables`：现有出题变量，包括case_title、disease、case_mode、case_context、case_timeline、biomarkers、decision_points、adverse_events、evidence_notes等。
- `data_quality_notes`：原文缺失、冲突和OCR不确定项。
- `source_notes`：字段对应的实际来源标签或段落位置；不输出原文件链接、文件名。没有真实页码不编页码。
- `review`：独立模型核对结果，不是医学审核。
- `requires_human_confirmation=true`、`ready_for_generation=false`：输出始终是待人工确认草稿。确认流程需由现有业务层处理，不以改一个布尔值代替核对。

`case_id`留空由业务分配；`learning_points`留空由运营/用户指定；`question_count`和`difficulty`不从病例推断，沿用出题流程的配置；不输出`question_draft`或`review_feedback`来覆盖出题循环状态。`case_intro_images=[]`，不自动把患者图片放进公开病例。六类癌种用现有名称，其他癌种保留在disease，不硬塞进六类；second_cancer_type保持空。

病例时间轴保留实际治疗经过；decision_points使用“当时已知信息＋待回答问题”。完整变量只供内部出题使用，不能直接将全程治疗结局全部展示给答题前的学员。

本地代码仅做部分身份标签遮蔽及输出拦截，模型也有脱敏要求；不能保证完全脱敏或医学事实完全正确。优先上传已脱敏资料，人工核对年龄、日期、药名剂量、病理/检测方法、分期矛盾及患者标识。

## 首次平台验证

每次只测一份已知资料，检查完整运行记录与原文：

1. 文字PDF：病程、病理、检测结果是否齐全。
2. 扫描PDF：确认平台实际调用增强解析并读出文字；如果读不出，先检查服务，不调整提取提示词掩盖问题。
3. 多张报告照片：返回数量、顺序和OCR文字是否对应。
4. HTML文件及仅draftData：确认正文提取，内嵌报告图片是否被保留并OCR。
5. PDF＋照片：确认最终仅输出一份合并JSON，不漏掉任一路材料。
6. 空输入、坏链接、图片空页：应输出insufficient及原因。

导入兼容性、跳过分支的变量默认值和调度、OCR插件权限、PDF增强服务、实际模型输出、手机端上传都尚待平台实测。当前仅完成离线代码与导出结构检查；详见`离线校验报告.json`。
