# OCR文本入口完整工作流

交付文件：OCR文本清洗与五题生成-完整工作流.json。

这是用户本次上传工作流的完整改版，不是局部节点、提示词片段或待执行补丁。包含10个节点、10条连接，以及原有题目生成子应用绑定。

## 输入与流程

把一例病例的上游OCR文字作为用户问题传入，可以是：

- 纯文本；
- 同一病例各页文字的字符串数组（直接API调用仍按接口要求放入用户问题）；
- 粘贴JSON字符串数组，例如["第1页OCR文字","第2页OCR文字"]。

输入数组各段按顺序用空行连接，不将多例病例混在一起。上游OCR应输出识别后的实际文字，不能只给图片URL或文件URL。

流程开始 → OCR文本输入整理 → 正文清洗（OCR文本） → 病例结构化提取 → JSON格式修复 → 代码运行 → 原有题目生成子应用 → 单组候选检查与终稿输入 → json生成 → json输出。

## 已改动

- 删除文档解析节点，关闭文件/图片上传入口。
- 原HTML正文检查改为OCR文本输入整理，输入直接引用流程开始的用户问题。
- 清洗提示词改为处理OCR重复页眉、水印、断行、身份标识和串列表格；区分患者事实、组内意见与参考研究。
- OCR事实歧义写入待核对项，不推断尺寸小数点、基因位点、分期或检测属性。病例提取保留这些不确定性。
- 两个AI节点均关闭视觉、音频、视频及文件提取，直接处理文字。
- 结构化字段、分类白名单、14字段病例载荷、题目生成应用绑定与最终组装代码保持。
- transport_mode不再引用整份OCR正文，当前为普通单例JSON返回。旧文件批量应用以“文件+批量控制标记”调用的方式不适用于本OCR文本入口；将来如需批量，应由上游按病例逐个发送OCR文字并汇总。

## 导入

建议导入到原有单例预处理应用，并确认“题目生成”节点仍指向原出题子应用；新建应用时需要在该节点重新选择自己的出题子应用。此文件保留了用户附件中的调用绑定，但无法在本地确认线上应用访问权限。

模型设置忠实沿用本次附件：两个AI节点为qwen3.8-flash。若你在线正在试GLM 5.3 Flash，导入后在两个AI节点的模型下拉框重新选择平台中实际可用的GLM型号；本文件没有猜测自定义渠道的模型ID。题目生成子应用内部的模型不由这个外层JSON修改。

## 已验证

六项离线检查通过：完整JSON及代码语法、连接和变量引用、数组文本依序保留、空输入与错误类型拒绝、下游接口保持、文字模式及原模型设置保持。没有付费模型调用，线上导入与生成效果未验证。清洗提示词不等于对OCR内容的医学事实审核。
